# 先检索库内旧实现，再决定新写（复用优先）

**先过适用判据**：改动要**新增一段有实际逻辑的代码**（新模块 / 新函数 / 新流程 / 新数据结构）才走本流程。纯配置、纯文案、单行修复、已有 skill 明确指定路径的改动，不适用。

**核心红线**：凭空新建之前，必须证明"库里没有能直接或改造后复用的旧实现"，或写清为什么不用。**"我没见过 / 我没搜到" ≠ "不存在"。**

## 何时加载
- 新增功能 / 接口 / 字段 / 模块 / 命令前；
- 准备复制粘贴一段旧代码、或大改它来做相似的事时；
- 提交前自检：这段逻辑是不是重复造轮子。

## 检索流程（多重入口，至少覆盖 4 类）
1. **词形拆词**：把功能名拆成子词再搜，覆盖 `camelCase` / `snake_case` / 中文注释。例：`UserProfileCache` → `profile`、`cache`、`用户资料`。
2. **同义词轮搜**：`search/find/query/lookup`、`remove/delete/drop`、`fetch/load/get` 换着搜。
3. **结构搜索**：装了 `ast-grep` 就按 AST 形状找同类写法（"所有这种错误处理 / 这种查询构造"）；否则用 `rg` 搜调用点 `rg 'name\('`、定义 `rg 'fn name|def name|function name'`。
4. **历史与邻域**：`git log -S'<标识符>' --oneline` 看这块怎么演化；`rg --files | rg '<模块名>'` 找相近模块；读该目录 README 与测试，测试常直接暴露已有能力。

> **优先调用 `relation_search` 工具**（dsh-relation-search 插件提供的 BM25 词项召回 + ast-grep 结构召回）：`query` 填功能名 / 标识符 / 中文描述，可传 `astPattern` 做结构召回；拿它做第一轮召回，再用 `rg` / `ast-grep` 精查。工具不可用时用上面的手工入口，不许跳过。

## 候选评估 → 三选一（逐条给结论）
对召回的前几条（建议 3–8 条）逐条判定：
- **直接复用**：原样调用，指出可复用的符号与位置。
- **改造复用**：改哪些、为什么改比新写便宜；给出改造点。
- **不复用**：写清**具体差异**——旧实现卡在哪条约束（性能 / 语义 / 依赖 / 副作用 / 耦合），指到文件:行号或具体行为，而不是"感觉不合适"。

## 决策记录（可核查的产物）
动手写代码前，在回复里留下最小记录：
```
检索：关键词 <...>；命中 <文件:行>、<文件:行>…
判定：<候选A> → 复用 / 改造 / 不复用（原因：…）
结论：<复用 A 改造> 或 <无可用旧实现，新写；与 A/B 的差异是 …>
```
没有这份记录 = 视为未检索。

## 反例 ❌
- ❌ 上来就新建文件 / 新函数，一次检索都没做；
- ❌ 只搜一个关键词、"没搜到"就断定不存在；
- ❌ 搜到了相似实现，却因为"改起来麻烦"直接新写，不说明差异；
- ❌ 复制一段旧代码改改就叫复用，却不指出来源与差异。

## 边界与分工
- 检索**外部开源先例**（业界成熟实现）→ `prior-art-survey`；本 skill 只管**库内既有代码**。
- 结论要给可核查证据 → `proof-chain`；本 skill 的"决策记录"就是它在复用场景的实例。
- 改动越界成行为变化 → `refactor` 界定边界。
- 新增功能先写不变量 → `invariants-first`。

## 强制点
本 skill 是策略层，硬机制是"检索产物"这道门：**新增有逻辑的文件 / 新增对外函数前，必须贴出检索关键词 + 候选清单 + 逐条判定**，缺则按未检索打回。装了 dsh-relation-search 插件时，第一轮召回由 `relation_search` 工具完成（结构 + BM25 双路召回），skill 只负责"怎么用召回结果、怎么写决策记录"。
